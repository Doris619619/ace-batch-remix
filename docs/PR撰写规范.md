# ACE Batch Remix PR 撰写规范

创建或更新 Pull Request 时，正文必须按本文件的结构与风格书写，不得只写一两句空泛摘要。目标是让审查者在不翻完整 diff 的情况下，理解**做什么、为什么、怎么改、影响什么、怎么验**。

## 强制结构

PR 正文按以下顺序使用二级标题；某一节确实无内容时，写一句明确说明（例如「无 ACE-Step API 映射变更」），不要整节省略到审查者不知道是否遗漏。

```markdown
## Summary

## 背景

## 改动（逻辑）

## 改动（代码）

## 影响

## 验证

## 材料
```

「改动」必须拆成两节，禁止合并成单一的 `## 改动`：

- **`## 改动（逻辑）`**：从**使用者工作流 / 批处理行为**写——用户如何配置 Caption、选择输入、恢复任务、获取输出；说明行为变化与安全边界。尽量少提文件路径与实现细节。
- **`## 改动（代码）`**：从**实现落地**写——模块 / 路径、ACE-Step API payload、manifest 状态、下载安全性、非显然的重试与恢复决策。审查者靠这一节对照 diff。

### Summary

- 用 3～6 条短 bullet，概括**用户或系统可观察到的结果**，不要罗列文件名。
- 关键点结论可用 `**加粗**`，其余句子保持克制，不要整段加粗。
- 若覆盖 issue、承接已合并 PR、或本分支是某条线的唯一待审 PR，在 bullet 之后用一两段散文交代关系（编号、合并状态、当前审查重心）。

### 背景

- 说明需求从哪来、约束是什么、为什么现有实现不够。
- 写清关键设计取舍：采纳了什么、砍掉了什么、各自的理由。
- 合规、安全、账号模型、平台限制等「决定实现形态」的事实优先写在这里，而不是埋在改动细节里。

### 改动（逻辑）

- 按用户工作流或功能块描述行为变化，例如「首次联调可通过 `--file` 只提交一首歌，正式运行默认仍处理全部 `input/`」。
- 写清前后对比：以前如何提交、恢复或下载，现在如何操作，以及减少了什么风险或人工步骤。
- 可包含批处理规则（只读健康检查、任务失败隔离、断点续跑、输出不覆盖），但不要展开到内部状态机。
- 读者应能在不看代码的情况下理解这次 PR 对日常运行与数据安全的影响。

### 改动（代码）

- 按模块 / 包 / 目录写清实际落地内容，可点名关键路径与公共 API。
- 解释**非显而易见的命名、分层、并发、鉴权、schema、布局算法**决策，而不是复述每一行 diff。
- 对容易误读的点主动说明「为什么叫这个名字 / 为什么不放在别处」。
- 客户端 PR 应写清请求是否会重投、状态如何落盘、临时文件何时原子替换，避免「逻辑」与「代码」两节内容重复粘贴。

### 影响

- 写清对现有用户、配置、开关、迁移、生成代码、上下游仓库的影响。
- 明确「没有什么」也很重要（例如：无 feature 开关、无新后台任务、不落库某类数据、不改任务业务规则）。
- 若含大范围生成物或顺带 regen，单独说明哪些是噪声、哪些是实质行为变化。

### 验证

- 列出已执行的检查与结果（构建、类型检查、测试、迁移、真实账号联调、桌面端打包等）。
- 已完成的用文字或 ✅ 标明；仍需人工 / 上线后确认的用 `- [ ]`。
- 写明验证边界：哪些告警/失败与本 PR 无关。

### 材料

- 链接设计文档、相关 issue / PR、前端或后端配套 PR。
- 本项目为 CLI；材料节应说明「无 UI 截图」，并列出真实 ACE-Step 联调或 Mock API 的验证边界。

## 写法要求

- 用中文写审查者真正需要的信息；专有名词、API、路径、命令可保留英文。
- 先讲结论与约束，再讲实现细节；**逻辑节讲体验，代码节讲落地**，两节不要互相拷贝。
- 一次 PR 对应一条可审查的主线；若历史演进复杂，在「背景」里交代，不要把无关工作塞进同一 PR 却不说明。
- 不要粘贴大段无关日志；必要命令与结果用短句概括即可。

## 正文骨架

复制以下骨架填写（删除括号提示语）：

```markdown
## Summary

- （可观察结果 1）
- （可观察结果 2）
- （可观察结果 3）

（可选：与 issue / 前序 PR / 本线唯一待审 PR 的关系。）

## 背景

（需求来源、约束、为何决定当前实现形态；砍掉的方案及理由。）

## 改动（逻辑）

- （用户怎么操作 / 界面怎么变 / 交互路径如何变短）
- （关键体验规则：保存、取消、对齐、拖拽边界等）

## 改动（代码）

- **`path/or/module/`**：（做了什么、关键 API / 行为、非显然决策。）
- **`...`**：（……）

## 影响

- （对用户 / 配置 / 数据 / 生成代码 / 依赖方的影响）
- （明确无影响的边界，如无新开关、无后台任务、不改业务数据结构等）

## 验证

- （命令或检查）✅ / 结果简述
- （真实环境或端到端）……
```

## 风格参考（结构示意）

下列示例展示的是 ACE Batch Remix 所需的信息密度与段落组织方式；撰写本仓库 PR 时套用同级结构与深度，替换为本次真实改动。

```markdown
## Summary

- 用户可用 `--file` 或 `--limit` 做**单首 Smoke Test**，正式运行不带筛选参数时仍批量处理全部输入。
- 客户端对 `/release_task` 的读取超时进入待人工确认状态，**不会自动重投**可能已被服务端接受的任务。
- 生成结果只在两个 MP3 均完成下载后标记 completed；输入、输出、日志与 manifest 不进入 Git。

## 背景

远端 ACE-Step、SSH Tunnel 和 GPU 模型不属于本仓库，因此本项目只通过本机 HTTP API 提交任务与下载结果。首次模型加载可能耗时较长，不能把提交超时直接等价为服务端未接受任务。

## 改动（逻辑）

- 用户把音乐放入 `input/`、填写统一 Caption 后一次运行完成批量处理。
- 联调与调参时，用户可临时指定一首和 Caption，不会污染正式配置或提交其余歌曲。
- 下载中断后只重试下载已完成任务，不重复生成已经完成的歌曲。

## 改动（代码）

- **`src/api.py`**：集中维护 ACE-Step Remix payload 与 `/health`、`/release_task`、`/query_result`、`/v1/audio` 的调用。
- **`src/runner.py`**：维护 manifest 状态迁移、单首选择、输出原子写入与不确定提交保护。
- **`tests/`**：用 Mock API 覆盖上传、轮询、恢复、下载失败与 Unicode 路径。

## 影响

- 无数据库、Web UI、Docker 或远端部署变更；不修改 ACE-Step 源码。
- `input/`、`outputs/`、`logs/`、`manifest.json` 始终受 Git 忽略保护。
- 如改动 API payload，应说明真实服务器版本、schema 证据与仍需人工验证的声学效果。

## 验证

- `python -m unittest discover -v` ✅ / Mock API 回归测试通过。
- 真实 `/health`、单首 `batch_size=2`、两个 MP3 下载与 manifest 落盘：按实际执行情况记录。
- [ ] 最终 Caption 确认后，再执行 20 首 × 2 的正式实验。

## 材料

- 工程协作规范：`docs/工程协作规范.md`
- 真实 API 联调记录或相关 issue / PR：……
- CLI 工具，无 UI 截图
```
